# Source-backed hierarchical table candidates

`pdf2data table-records extract --package PACKAGE --rules RULES.json --output NEW_OUTPUT --json` reads an immutable verified L1 package. It does not reparse/OCR the PDF, call a model, update source quality or publish data. `pdf2data table-records verify --bundle OUTPUT --json` pins source/rules/code hashes and performs full bounded native re-derivation; changing/re-hashing an output cannot bypass replay. Use a new output directory outside the source package. SDK entry points are `table_records.extract`, `compute` and `verify`.

Rules use `pdf2data.table-record-rules.v1`: explicit selected table IDs, role → column indices, optional per-fragment column maps, declared origin header rows, ordered group levels with `any`/`all` marker roles, optional four period roles (start/end/days/charge), summary roles/owner level and exact status literals. Company/application/tranche is one configured hierarchy, not a hardcoded legal ontology. Rules and output schemas are in `schemas/table-record-rules.schema.json` and `schemas/table-records.schema.json`.

Output `pdf2data.table-records.v1` retains source cells once, with native source pointers, PDF/package/page/table/version identities, cell-local text spans, geometry and source quality. Header/blank/data/period/incomplete/status rows reference these cells. Group markers, parent candidates, row memberships and reported summaries are distinct records. Blank/null/zero/false remain distinct; no values are filled down or assigned invented selected-page offsets. A source merged-cell membership is labelled separately from a configured sparse block. A shared application-ID cell does not duplicate its periods. Summaries stay once at the printed row and configured parent scope, rather than on every period.

Hierarchical associations remain unreviewed candidates. A new company resets lower scopes; a new application resets its capacity blocks. A new partial `all` marker clears that level instead of silently using the previous capacity owner. Missing ancestor context, incomplete period fields, reversed date candidates, incompatible columns and unresolved continuations are explicit gaps. Typed dates and numeric literals support inspection; source day counts/charges are not recalculated, currencies/units/scales are not inherited and no current COD, payment, financial liability, legal identity or applicability is approved.

Across adjacent selected physical fragments, continuation candidates require source page-boundary geometry, compatible column geometry/count, an origin header and either matching repeated header roles or a numeric/closing fragment bridging an open parenthesized cell in the same configured role. The latter is structural evidence, not reconstruction of the condition's meaning. Explicit column maps allow reordered columns. Changed declared/header units, unavailable geometry, missing pages and competing candidate fragments retain unresolved/ambiguous states and do not carry active contexts. Header rows are retained and excluded from data groups. Cross-page memberships retain the full candidate-chain IDs. Split periods stay separate incomplete fragments; they are not assembled into fabricated complete periods.

These cues do **not** independently check intervening body text/new sections: `intervening_body_content_checked` stays false, and every continuation/membership requires review. The tool does not claim universal table identification or verified semantic ownership. Similar layouts alone do not establish continuity. A caller must bound/authorize the selected family and inspect unresolved source/context states before using a derived association.

The worker has a 1–600 second timeout, row/cell bounds, a 128 MB result bound, strict JSON, source/code/rule change checks and no partial-success output after a failure. Runtime code adds no mandatory dependencies. Extracted packages still need PDF2Data's existing PDF verification dependencies. Prior cell/page-field defaults and producer implementations are unchanged by this opt-in protocol.

Development tests cover company resets, shared application IDs, partial commissioning/status-only rows, sparse/merged rows, two/three-page repeated headers, reordered columns, changed units, incomplete rows, missing pages, competing fragments, source immutability, summary scope, blank/null/zero/false, wrong rules, budgets, replay tampering, approval flags, duplicate JSON and worker timeouts. Real CTUIL and CERC source-case evaluation is separate from these synthetic tests and from independent human/legal review.

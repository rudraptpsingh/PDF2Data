# PDF2Data: measured extraction results

Follow-up: the [layout-guided pipeline](2026-10-31-layout-results.md) reaches 71.75% on the same frozen suite. The measurements below remain the original native/automatic baseline.

31 October 2026. The benchmark integration is implemented and locally validated.
Two real export defects are fixed. **General OCR quality remains insufficient
for unattended use on difficult documents.** The test results below keep that
separate from successful processing and legal review.

## Scope and method

Seventy source PDFs were frozen before inference: ten in each olmOCR-bench
category, selected by seeded filename hash. They contain **429 public rules**;
70 baseline checks give **499 evaluated outcomes** per profile. Dataset revision
and evaluator commit are pinned in the [guide](README.md) and
[provenance](receipts/suite-provenance.json). No annotation text is added to model
input. The evaluator uses upstream rules, not the olmOCR recognition model.

The full 1,403-document benchmark was **not run**. A full-download attempt hit
HTTP 429; the subsequent frozen sample downloaded successfully. Initial
harness-path failures were excluded as invalid harness runs. The recorded
native-before baseline is the subsequent valid run, with its one actual parser
failure retained in the denominator.

## Comparison

The coverage-adjusted macro averages seven public categories plus the baseline
category. It is a predicate score, not character accuracy or legal accuracy.

| Profile | Completed PDFs | Adjusted macro | Passed outcomes / 499 | Extraction wall time |
| --- | ---: | ---: | ---: | ---: |
| Before fixes: native + tables | 69/70 | 15.73% | 73 | 12.45 s |
| After fixes: native + tables | 70/70 | 15.91% | 74 | 11.47 s |
| After fixes: automatic OCR + tables | 70/70 | 21.53% | 101 | 40.77 s |
| Same automatic extraction, text only | 70/70 | 16.68% | 80 | Reuses the 40.77 s run |

The fixes recover a failed document; they do **not** demonstrate a broad OCR
accuracy gain. Automatic OCR is an existing recognition profile, measured here
against native extraction. Compared with the fixed native profile, it adds
**5.62 percentage points** to the adjusted macro at about **3.6 times** the
single-run processing time. The seven public categories alone, excluding the
baseline, score 9.00% native versus 12.98% automatic OCR.

Raw upstream macro rates are 27.50% before/native, 27.68% fixed/native and 21.53%
automatic. Native empty outputs can pass absence predicates; that inflation is
why raw and coverage-adjusted numbers are both retained. No raw-rate improvement
is claimed. See the [complete comparison](receipts/comparison.md) and
[machine-readable receipt](receipts/comparison.json).

Table-preserving automatic output scores 20/56 table predicates; its text-only
ablation scores 0/56. Preserving structure therefore matters, but **table
recognition did not improve over native extraction** in this sample. These are
additive table candidates; the benchmark does not prove inline placement or
absence of duplicate table text. Zero mathematical-rule passes is a substantial
limitation, not an evaluator success to hide.

Native and automatic release profiles share source, implementation and runtime
fingerprints. Both use four workers, no resume and zero reused cases. Automatic
selection used native text on 27 pages and Apple Vision on 43. Device reporting
is `system_managed_unreported`: GPU use is not established. OS caches were not
cleared, hardware was shared, and no repeated latency distribution was measured.
Do not interpret the native timing difference as a demonstrated speedup.

## Defects found and fixed

**Unicode record boundaries.** A public multicolumn PDF produced literal U+0085
inside a JSON string. Python `splitlines()` treated it as a record boundary and
caused the package to fail. JSONL readers now split physical LF records while
preserving U+0085, U+2028 and U+2029 inside source text. No source characters are
removed. Local legal database/vector consumers receive the same correction.

**Irregular table grids.** Extractor row indices and global geometric columns
could disagree, allowing a merge to cover a populated cell. Values now map by
source bounding-box coordinates. Original extractor rows remain in
`extracted_cells`; canonical `cells` retain covered blanks and merge spans.
A multiplicity check rejects unmapped populated values. Table-version hashes
include the canonical grid and mapping version, preventing stale cell-ID reuse.
Existing packages remain immutable; reprocess into new packages to obtain fixes.

The affected PDF is bound by source SHA-256
`382a90f646126c1569df780f7082dec3a5c78792f4135bdb31427af96939c35d`.
Both fixed profiles complete it. Processing success does not certify its OCR.

## Legal and formatting controls

Two original legal/regulatory PDFs (eight pages) pass seven source-checked
regression probes plus eight baseline checks. These include:

- Illustration 1 retains `31.12.2027`; Illustration 2 retains `Not effective`.
- `Not effective` remains under `GNA effectiveness date`, between `01.06.2027`
  and `30.07.2026`.
- The second illustration's SCOD and adjacent contract/final-grant values stay
  in their columns.
- Optional rejoinder wording retains `if any` and `within two weeks thereafter`;
  the listing date remains `8.10.2026`.

These are custom regression controls checked against original page images,
**not a blind legal benchmark**. Three freshly CLI-processed/exported documents
(ten pages) additionally pass checks for 36 distinct illustration cells, inline
table order, footer separation, exact source partitions and a paragraph joined
across pages. A fresh generic merged-header/nested-list fixture also passes.

Final suites: **406 PDF2Data tests passed**, one optional `docling_core` dependency
skip; **120 local legal-pipeline tests passed**. Corruption, missing coverage,
invalid merges, Unicode preservation, exact spans, source hashes and downstream
retrieval are checked. The independent source/output reviewer recomputed the
score arithmetic and checked populated-value conservation across 22 tables.

All 70 automatic cases completed, but **44 pages retain review flags**. Legal
interpretation, currentness, company applicability and filing approval remain
separate. No Cloudflare resource, remote DB or deployment was changed.

## Next improvements, ordered by measured weakness

1. Add a layout/math-capable recognition backend behind the same CLI, then score
   it on this unchanged suite. Require better public-category results rather
   than promoting it based on a few attractive pages.
2. Improve high-resolution region reading and column ordering; retain competing
   readings and source geometry instead of fabricating normalized text.
3. Add scanned-table recognition and cell-level critical-token comparisons.
   Existing ruling-derived candidates cannot cover every scanned/complex table.
4. Run the full pinned dataset, OmniDocBench structure metrics and a blind legal
   holdout with independently checked dates, amounts, conditions and orders.
5. Measure repeated warm/cold latency, memory and actual accelerator use before
   making throughput or GPU claims.

The adapter and regression fixes are ready for review. The measured difficult-
document quality is not a basis to remove source review or legal-publication
controls.

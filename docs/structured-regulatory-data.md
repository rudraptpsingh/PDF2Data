# Structured evidence for search and calculations

PDF2Data should supply source-linked structure and observations. A downstream
domain layer should turn those observations into reviewed rules, connect verified
client facts, and invoke deterministic calculation tools. The current parser
implements metadata and presentation candidates; it does not yet implement
complete regulatory rule interpretation or client eligibility calculation.

## Document identity and bilingual metadata

`document-metadata.json` is generated by both readable export paths and is also
included under `document_model.metadata` in `data.json`. Each field records its
candidate role, original label/language, literal value, separate label/value
spans, source page hash, physical geometry when available, context and date
normalization status. No source text is overwritten.

The reviewed memorandum has two separate first-page fields:

| Role | Literal | Normalized value | Position |
| --- | --- | --- | --- |
| Document reference | `L-1/250/2019/CERC` | Original identifier retained | Left |
| Document date | `26.10.2026` | `2026-10-26` | Right |

The overlay shows these fields independently instead of one undifferentiated
metadata rectangle. Their parent block remains intact. The reference is shared
by multiple companion documents and versions, so it is not a unique document key.
Use the source PDF hash plus version/type relationships to distinguish them.

Label interpretation is document-type-sensitive: `Date of Order` supplies a
decision-date candidate, `Date of Hearing` supplies a hearing date, and a registry
list's `as on` supplies a listing-as-of date. A hearing date never substitutes for
an issue date. Narrative publication/effective dates remain body mentions. Unclear
numeric dates such as `03/04/2026` retain both interpretations with ISO null.

Hindi aliases include `दिनांक`, `संख्या`, `याचिका संख्या`, `सुनवाई की तिथि`,
`आदेश की तारीख` and related variants. Both scripts and their original digits are
retained. Devanagari digits and recognized Hindi/English month names may be
normalized for comparison. This does not translate identifier text or resolve
an unknown calendar.

In the real bilingual Gazette, `फरवरी 10, 2010` and `FEBRUARY 10, 2010` yield the
same date candidate. Hindi and English notification identifiers share numeric
components. Both are review-required correlations, not verified text equivalence.
The Hindi OCR reading `4 फरवरा, 2010` retains an unrecognized-month status even
though the English side reads `4th February, 2010`. The Gazette also has distinct
publication and notification datelines; the extractor leaves its primary issue
date unestablished instead of choosing one. The scan's original quality flag is
retained.

## Measured document-type patterns

The local profile covers **13 unique PDFs, 138 pages and nine source-declared
types**. It counts English/Hindi aliases separately, including reference/date
labels, notifications, drafts, proceedings, parties, commencement, waivers,
charges, rates and tables. It records total occurrences, first-page occurrences,
unique-document frequency and occurrences per 1,000 whitespace tokens.

Repeated footers can increase occurrence counts; they do not increase the number
of unique documents containing a keyword. The sample is small, uneven and mostly
English. Missing Hindi OCR matches do not prove that a Hindi source label is
absent. Frequencies guide rule review; they do not automatically train a type
classifier, approve metadata or measure extraction precision/recall.

Use the CLI over verified existing packages, without another PDF reader:

```sh
pdf2data profile-documents --manifest profile-input.json --output NEW_DIR --json
```

The input contains `schema_version: "pdf2data.profile-input.v1"` and a `packages`
list of objects with `package` paths and optional IDs. Package paths resolve
relative to the manifest. Sources are verified and deduplicated by PDF hash.
Outputs include JSON profiles, a CSV frequency matrix, a short report and
source-bound metadata for each PDF. Original packages are unchanged.

## What a calculation needs from extraction

| Data layer | Required structured information | Why it matters |
| --- | --- | --- |
| Document/version | Issuer, identifier, type, issue date, draft/final context, amendment relationships | Prevents applying a proposal or superseded rule |
| Clause structure | Clause ID, complete parent text, subclauses, conditions, exceptions and cross-references | Prevents retrieving a rate without its qualifying conditions |
| Tables | Stable table/cell IDs, header paths, units, row/column spans, footnotes, blank-cell state | Binds each rate to the correct date band or category |
| Numeric observations | Literal, decimal candidate, currency/unit/scale, denominator, period, operator and source span | Distinguishes percent, MW, money, years and limits |
| Rule interpretation | Actor/role, jurisdiction, trigger, predicate tree, exceptions, variable bindings, caps, effective intervals | Establishes which calculation may apply |
| Client/project facts | Verified entity/SPV, charge-bearing role, connectivity, technology, contracts, COD and relevant dates | Establishes applicability and exposes missing inputs |
| Tool execution | Reviewed rule/version, fact IDs, typed inputs, rounding, result and trace | Makes the numerical answer reproducible |

The parser currently retains literal quantity mentions and table structure.
Binding every quantity to an eligibility predicate, exception and outcome remains
domain-layer work. A list of percentages is not an executable rule. Formatting
alone cannot establish legal precedence or applicability.

## Real source and illustrative arithmetic

The [machine-readable handoff](examples/regulatory-calculation-handoff.json)
uses the memorandum with source SHA-256
`17b7dd0fe13e4e4f1ca5d4793c7485d66bb5e1b527f9b846a44564577f4d49ff`.
Page 5, Illustration 1(b), describes a proposed 75 percent waiver for a ten-year
PPA tenure. It also discusses extension up to a 25-year COD-based cap, and a
different trajectory if the buyer changes or the contract terminates. The full
973-character source paragraph and its exact offset are retained in the example.

An interpreted candidate must retain all those conditions and the references to
Table 1 of Regulation 13(2)(a), Regulation 13(2)(h), and proposed subclauses. The
baseline's “whichever is later” comparison also needs the correct connectivity
date and SCOD inputs. A 25-year cap must not become an unconditional 25-year
benefit when the illustrated PPA lasts ten years.

For arithmetic only, assume a monthly pre-waiver charge of INR 1,000,000 and that
the candidate 75 percent rate applies. Decimal arithmetic yields a waiver of
INR 750,000 and payable charge of INR 250,000 for that month. The base charge is
hypothetical, eligibility remains unknown, and the draft-context rule is not
activated for operational use. This demonstrates arithmetic, not client impact.

The proposed tool contract uses allowlisted operations such as percentage
reduction, tariff-band lookup and calendar-date comparison. It accepts explicit
typed inputs and returns a trace. PDF text and model-generated formulas must not
be evaluated as arbitrary code. Percentage bounds, currency/period consistency,
scale, rounding and missing facts need validation. Calendar months and years
require calendar arithmetic rather than a fixed number of days.

## Search and answer integration

Index source identity, document family, typed date roles, normalized identifiers,
clause/table IDs and language alongside text. Exact structured filters can narrow
the candidate documents before lexical/semantic retrieval. Retrieve complete
clauses, exceptions, referenced tables and related versions before deciding
eligibility. Citation resolution and the rule graph need explicit provenance.

The answer should separate source statements, applicability findings and tool
results. Unknown client facts or unresolved source values should produce a
missing-input response. This change provides the JSON foundation; it does not
modify a database or establish a measured search-latency or answer-quality gain.

## Validation gates

- Preserve raw page hashes and verify every metadata/quantity/cell source anchor.
- Evaluate field roles separately from OCR correctness and date normalization.
- Test Hindi/English agreements, conflicts, ambiguous dates and unknown months.
- Evaluate condition/exception and table-header bindings on independent labelled cases.
- Block operational rule activation until version/status and interpretations are reviewed.
- Test mathematical boundary cases, units, calendar cutoffs and rounding independently.
- Evaluate retrieval completeness and the final answer's claims, not citations alone.

The local suite for this change passed **1,096 tests**, with one optional
`docling_core` dependency test skipped. Corpus frequency counts and source-bound
candidate checks are additional observations, not a legal/metadata accuracy score.
